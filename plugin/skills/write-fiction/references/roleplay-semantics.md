# Roleplay semantic kernel and causal beat

`runtime.kernel` is a compact, source-linked entry-context index for hero, scene, and leader. It reuses active inventory fact IDs and existing validated `scene_context` field/index declarations. It does not duplicate source claims or add an inline provenance format. Each item has a unique ID, a closed layer/slot, a ref, optional holders, and links. An omitted holder means leader-only. Hero references must target active facts already projected to the hero; `leader_only_context` is never a hero ref. `not_established` uses `ref: {"unknown_id":"..."}` for a declared inventory unknown and is leader-only; the projection retains its `gap` and `blocks_when` fields. A scene tension links to a hero goal, stake, or value; a condition names `defeated_by` perceiver classes. NPC kernel entries ground motive and access through existing scene-context references. A disconnected item is allowed only with `background: true`, but the kernel still needs a live hero goal/stake/value, a live scene affordance/condition/tension, and a link joining those anchors; an all-background kernel is invalid.

Allowed links are `threatens`, `enables`, `limits`, `conditions`, and `informs`. `informs` can connect evidence or context to personal significance; it does not assert a physical cause. `condition.defeated_by` names how the affected actor can overcome that condition. For a cord whose effect depends on being unknown and unnoticed, the affected intruder must know about or notice that cord/presence; generic knowledge of an alarm rule is insufficient. The item's `holder` describes who has access to that entry context and does not automatically identify the affected actor or disable the condition. There are no kernel slots for emotion, required reaction, outcome, focus, or hero choice. Machine validation checks the shape and references, not whether a cited source supports the claim or whether an event is tactful.

The host records each significant new external stimulus in `turn.event`, separate from `situation`. It identifies an origin, a cause, an access channel/path, perceivers, relevance, and hero-visible observations where the hero perceives it. Relevance is either `ambient` or a non-empty list of existing kernel IDs. A `kernel` cause references a local kernel ID, `prior_event` references an earlier event in this branch, and `hero_action` uses `turn:<number>` for an earlier recorded hero action. `hidden`, `offscreen`, and `accident` causes require both private `detail` and a typed local `basis`, for example `{"kind":"prior_event","ref":"event_1"}`; valid basis kinds are `kernel`, `prior_event`, and `hero_action`. `access.detail` describes the physical or perceptual path by which the event became available. The event's `observations` must be nonempty and included in `revealed_to_hero` whenever `hero` is a perceiver. Hero and formatter projections receive only an observed event ID and its observations, through one allowlisted projection. Private causes, access details, leader-held kernel items, and private NPC knowledge stay out of hero history and the accepted prose skeleton. An event is not mandatory for ordinary action resolution or continuation.

The host attaches a hero action to a perceived current/prior event with `stimulus_ref`, or records `own_initiative`. Optional `meaning_ref` points only to a hero-visible kernel item. The hero writes natural action prose; the host does not ask for IDs or a reaction questionnaire. Perception, personal meaning, restraint, and manner appear only when they matter to this character and are played in the action text. No fixed emotion or bodily gesture is required.

Leader memory may use holder `world` or `npc:<id>`. NPC memory requires a `basis_event` perceived by that NPC. When carried into a continuation, NPC-held records retain their source session, branch, story time, holder, and basis as historical origin; they do not become current-branch NPC knowledge or authorize current actions. This distinguishes world state from a character's evidence or belief without creating a separate reader-access store. Initial NPC motive/access is explicit leader-only scene context. Existing hero state, memory, and consequences remain the mechanism for physical/resource continuity; there is no new item simulator. Source-backed kernel values describe entry context: later observations, consequences, and accepted character changes govern the current state.

An `issue` action requires a non-empty category and records a concise open problem, pauses the branch, and invalidates skeleton acceptance. The full issue list is leader-only status/context. `resume` changes branch status but does not resolve an issue or dispatch a role; open issues block both skeleton acceptance and finishing. There is no issue-resolution or turn-amendment action, so continue in a new branch if the flagged history must be replaced. Before each new beat, the host checks access, relevance, freedom from forced choice, and absence of leaks. This check is semantic review, not a stored or machine-proven pass. A final skeleton preserves the played causal trace in natural text without turning the kernel into prose inventory.

Craft basis and scope: [Weiland on scene structure](https://www.helpingwritersbecomeauthors.com/how-to-structure-scenes/) and [motivation-reaction units](https://www.helpingwritersbecomeauthors.com/motivation-reaction-units/amp/); [Fate Core defining scenes](https://fate-srd.com/fate-core/defining-scenes); [Dungeon World GM guidance](https://www.dungeonworldsrd.com/gamemastering/); [Justin Alexander, Don't Prep Plots](https://thealexandrian.net/wordpress/4147/roleplaying-games/dont-prep-plots). These inform a local craft heuristic: meaningful stimulus and response, motivated actors, actual scene purpose, and situations with room for player choice. They do not establish a universal psychology, mandate escalating danger, or prove the semantic truth of a generated beat.
