# Каркас повествования в WebUI

Дата: 2026-10-26. Статус: дизайн реализован в исходниках; машинная и браузерная проверка выполнены на изолированных данных. Актуальные ограничения и результаты: [статус реализации](NARRATIVE-FRAMEWORK-IMPLEMENTATION-STATUS-20261026.md). Авторская визуальная приёмка отдельно не выполнялась.

## Задание и границы

Буквальное ТЗ: «Используя опус проектируй в webui использование каркаса повествования, как общей линии, так и возможности задать сюжетку на главу и чтобы можно было подсвечивать закрытие этапов повествования и чтобы агент мог отталкиваться от согласованного каркаса повествования».

Результат этого задания — проект интерфейса и контрактов для реализации. Общая линия по умолчанию относится к открытой книге. Сквозная линия серии может связывать несколько книг, но отдельный редактор арок серии не входит в первую версию. Это явное проектное допущение, а не принятое автором сюжетное решение.

Ниже описаны предлагаемые продуктовые правила. Они не меняют канон, прозу, существующие авторские записи или принятые решения. Примеры этапов условные. Обязательная трёхактная схема, «путь героя» и автоматическая нарезка сюжета не вводятся.

## Проверенная основа

Проверены текущие рабочие исходники, включая существующие незакоммиченные правки:

| Источник | Фактическая опора для проекта |
|---|---|

| `web-client/public/chapter-workspace.js` | Выбор книги/рукописи, активная глава, несколько глав для агента, сохранение рабочих версий, защита от поздних ответов |
| `web-client/public/manuscript-model.js` | Раздельные идентичности новых и импортированных глав, конфликты и сохранение локальных правок |
| `web-client/manuscript-file.mjs` | Рабочий файл книги с CAS-версией; сохранение пропавших глав; данные приложения вне vault |
| `web-client/server.mjs` | Проверка активной книги и привязки рукописи; серверная сборка контекста, запрет готового клиентского manuscriptContext |
| `web-client/manuscript-context.mjs` | До 40 глав, 120 000 UTF-16 единиц с метаданными; превышение отклоняется без обрезки |

Карта понятий и категория «Сюжет» уже существуют, но в прочитанных компонентах нет модели согласованного плана и подтверждения его выполнения. Карта знаний не становится источником статуса «закрыт». Внутренний причинный каркас writer из редакторского протокола сохраняет своё назначение: он не заменяет публичный авторский план книги.

## Пользовательская модель

Три связанных объекта:

1. **Общая линия книги**: замысел, желаемый исход, ограничения и упорядоченные этапы. Несколько параллельных линий допустимы; одна может быть основной.
2. **Сюжетка главы**: что меняется за главу, локальные этапы, связь с этапами общей линии, границы знания и раскрытия.
3. **Подтверждение выполнения**: конкретный фрагмент рукописи и решение автора, что критерий этапа выполнен.

Этап общей линии может раскрываться в нескольких главах. Глава может продвигать несколько линий. Локальный этап может существовать самостоятельно, без родительского этапа. Связь «продвигает» не означает «закрывает».

Для этапа достаточно названия и ожидаемого изменения. Дополнительно доступны критерий закрытия, участники, порядок, предпосылки и запреты раннего раскрытия. Сложные поля свернуты. Причина/последствие описываются свободным текстом, без навязывания литературной школы.

## Размещение в WebUI

```text
Книга / рабочая рукопись                      [Каркас] [Контекст]
+------------------+-------------------------+-------------------------+
| Главы            | Текст главы             | Каркас                  |
| Глава 1   2/3    |                         | [Общая линия] [Глава]   |
| Глава 2   1/4    | выделенный фрагмент     | Согласовано: версия 3   |
| Глава 3   0/2    | с боковым маркером E12   |                         |
|                  |                         | E10 Завязка    Закрыт   |
|                  |                         | E11 Поиск      В работе |
|                  |                         | E12 Выбор      Проверить|
|                  |                         | [Связать с выделением]  |
+------------------+-------------------------+-------------------------+
Агент: Каркас v3 + сюжетка главы v2 + выбранные главы [Посмотреть]
```

Кнопка «Каркас» открывает новый режим существующего правого инспектора. Переключение между агентом, контекстом и каркасом сохраняет состояние; четвёртая постоянно открытая колонка не появляется. Есть раскрытие каркаса в основную область для большого плана. На узком экране — одна панель за раз с возвратом к прежнему месту текста.

Вкладка «Общая линия»: название линии, краткий замысел, этапы в авторском порядке; фильтр по линии/состоянию/главе, переключатель «Показать закрытые». Перестановка не меняет ID. У этапа видны связанные главы и доказательства закрытия.

Вкладка «Глава»: название текущей главы, цель и исход, локальные этапы, родительские этапы книги. Для ещё не написанной главы можно завести план без Google Doc и привязать текст позже. Смена активной главы меняет сюжетку, но не согласованную версию общей линии.

Оглавление показывает «2 из 3 закрыто» и отдельный признак устаревших подтверждений. Это счётчик этапов активной согласованной сюжетки, не процент качества главы. Без согласованного плана — «План не согласован» вместо 0%. План будущей главы находится в списке «Запланированные главы», пока не сопоставлен рукописи.

Карточка этапа: название → ожидаемое изменение → критерий закрытия → состояние → связанные главы/фрагменты. Основные действия: «Начать», «Связать с выделением», «Предложить закрытие», «Подтвердить закрытие», «Вернуть в работу». Для плана: «Предложить изменение», «Сравнить версии», «Согласовать показанную версию».

## Согласование и исполнение

Это две независимые оси; опубликованная версия плана неизменяема.

| Ось | Значения | Правило |
|---|---|---|
| Согласование | Черновик → На согласовании → Согласованная версия | Только явное действие автора создаёт активный снимок |
| Исполнение этапа | Не начат → В работе → Предложен к закрытию → Закрыт | Агент предлагает, автор подтверждает; автор также может сразу закрыть вручную |
| Проверка доказательства | Актуально / Требует проверки / Привязка потеряна | Вычисляется относительно текста; не переписывает историческое решение автора |

Изменение согласованного плана создаёт новый черновик. Пока он не согласован, агент продолжает использовать прежний активный снимок. Согласование новой версии общей линии не согласовывает молча связанные сюжетки глав. Показывается список затронутых глав; несовместимые планы получают «Нужно согласовать связь» и не используются как согласованные для нового writing-запроса.

Изменение содержания этапа создаёт новую revision этого этапа. Старое закрытие остаётся в истории, но не закрывает новую редакцию. Чистая перестановка сохраняет прежнюю revision содержания. Автоматически определять «тот же смысл» моделью запрещено: версия содержания меняется по детерминированному набору полей (название, ожидаемое изменение, критерий, предпосылки, запреты раскрытия, родительские связи); сохранить закрытие после переименования можно явным подтверждением автора. UI заранее показывает затронутые закрытия.

Прогресс имеет устойчивый ключ `(planId, stageId, contentRevision)`. `decidedInSnapshotId` хранит контекст решения, а не входит в ключ. Активный снимок читает прогресс своих ID/revision; отсутствие записи означает «Не начат». Перестановка и повторное согласование не сбрасывают закрытия. Решение принимается только для пары stageId/contentRevision в текущем активном снимке с проверкой его версии. «Предложен к закрытию» — вычисляемая надстройка при наличии актуального pending-предложения, а не второе хранимое состояние; отклонение возвращает прежний прогресс.

Согласованная сюжетка главы фиксирует родительские пары `(stageId, contentRevision)`. Она совместима с активным планом книги, только если все пары существуют и не архивированы. Другая revision или отсутствие пары требуют повторного согласования связи. Перестановка этапов общей линии эту совместимость не нарушает. Manifest содержит оба снимка и результат проверки закреплённых родительских пар.

В contentRevision локального этапа входят только parentStageIds без ревизий родителей. Закреплённые родительские revision хранятся на уровне снимка сюжетки. Повторное согласование связи создаёт новый снимок сюжетки, сохраняя revision и закрытия неизменённых локальных этапов; историческое закрытие локального этапа само по себе не доказывает выполнение изменённого родительского критерия. Для несовместимой сюжетки «Писать по каркасу» этой главы блокируется до согласования связи; молчаливого перехода к одной общей линии нет.

Архивирование этапа не является его закрытием и не удаляет историю. Общий этап не закрывается автоматически от всех закрытых дочерних: его собственный критерий может быть шире. UI предлагает проверить общий этап и показывает основания, но подтверждение остаётся отдельным.

## Подсветка закрытия

| Состояние | В каркасе | В тексте |
|---|---|---|
| Не начат | Пустой круг и подпись | Без заливки |
| В работе | Полузаполненный круг и подпись | Нейтральный боковой маркер |
| Предложен к закрытию | Янтарный значок «Проверить» | Пунктирный маркер, доступ к предложению |
| Закрыт, доказательство актуально | Зелёная галочка и подпись | Мягкая зелёная метка фрагмента по включаемому слою |
| Закрыт автором, цитата/окружение целы, глава правилась | «Закрыт автором · глава изменена» | Зелёный контур исторического решения с нейтральным значком; актуальный смысл не подтверждён |
| Закрыт ранее, цитата/окружение изменились | «Закрыт ранее · проверить фрагмент» | Янтарный маркер, без зелёного подтверждения |
| Привязка потеряна | «Фрагмент не найден» | Переход к сохранённой цитате в карточке |

Цвет всегда дублируется текстом/значком, управление доступно с клавиатуры. Слой «Этапы повествования» включается отдельно от форматирования и редакторских предложений; он не сохраняется как цвет авторского текста и не экспортируется в Google. При пересечении отметок виден общий боковой маркер с меню этапов, без наложения нескольких заливок. Фокус и screen reader раскрывают названия и статусы.

Закрытие вручную без текстового подтверждения разрешено с явной меткой «Подтверждено автором без фрагмента» и пояснением; зелёного фрагмента в тексте нет. Для доказательства из нескольких мест хранится несколько якорей; все обязательные основания должны оставаться актуальными. Новый текст не обязан заканчиваться закрытием этапа.

Слой этапов — отдельный CodeMirror StateField с предварительным mapPos и отдельным источником decorations/маркеров; он не использует очищаемый при docChanged marksField редакторского ревью. До сохранения и серверной валидации сдвинутые позиции предварительны. При авторской заливке вместо новой заливки используются подчёркивание и маркер на полях.

Локальная правка немедленно снимает актуальную зелёную заливку: изменение окна цитаты/окружения даёт предварительный янтарный сигнал, изменение вне окна — исторический контур с флагом. Границы якоря не расширяются при вставке на краях: start assoc=1, end assoc=-1; нельзя копировать противоположное поведение richField. Строгий режим — предпочтение пользователя для конкретной книги; его значение входит в manifest и меняет представление, а не исторические решения или семантическую валидацию. При закрытии без цитаты сохраняются хеши явно связанных глав; их изменение также даёт флаг непроверенного смысла. Если связанных текстов нет, решение остаётся явно бездоказательным, а не актуальным текстовым подтверждением.

## Устойчивые главы и якоря

Ввести app-owned `chapterId` UUID, отдельный от Google `sectionId`, названия и позиции. Он относится к книге и может существовать до текста. `textBinding` отдельно описывает local draft ID или Google document/tab/section/heading IDs, статус сопоставления и последний проверенный хеш.

Не переносить связи по одному заголовку или номеру. Однозначное совпадение существующего идентификатора позволяет сохранить связь; потерянная/неоднозначная связь требует сопоставления автором. Переход новой главы в записанную Google-главу сохраняет `chapterId` по квитанции создания, а не по похожему тексту. Смена основной рукописи сохраняет план книги, но не переносит доказательства на другой документ. Слияние/разделение глав — отдельное ручное сопоставление с сохранением истории.

Якорь содержит chapterId, identity источника, версию рабочего текста, SHA-256 текста, точную цитату, prefix/suffix, UTF-16 start/end. Сервер проверяет границы, surrogate pairs и точное совпадение с сохранённым рабочим снимком. При несохранённом браузерном тексте сначала успешно flush; при конфликте доказательство не сохраняется, выделение и текст остаются в браузере.

После правки внутри фрагмента или prefix/suffix он требует проверки с янтарным сигналом. Сдвиг до фрагмента допускает детерминированное перемещение только при однозначной точной цитате и окружении. При повторяющихся цитатах автоматический выбор запрещён. Удалённый фрагмент не исчезает из истории. Изменение главы вне окна цитаты/окружения сохраняет историческое авторское закрытие, но помечает семантическую актуальность как непроверенную. Нейтральный значок сообщает об этом без тревожной заливки всех этапов; tooltip объясняет, что зелёный контур означает прежнее решение автора, а не повторную проверку нового текста. В строгом режиме эта же ситуация получает янтарный сигнал. Агент в обоих режимах получает флаг непроверенного смысла. Действие «Подтвердить актуальность закрытий главы» показывает перечень, текущие фрагменты и версии, записывает авторское решение пакетно с CAS; без просмотра и подтверждения оно не выполняется. Актуальность расположения и актуальность решения о закрытии учитываются отдельно.

## Агент и согласованный каркас

Панель контекста перед отправкой показывает активную версию общей линии, версию сюжетки, выбранную задачу/этапы и главы. Команда «Писать по каркасу» использует только согласованные снимки. Если их нет — предлагает создать/согласовать план; обычный разговор и исследование доступны без него. Режим «Обсудить черновик плана» явно маркирует черновик и не выдаёт его за согласованный.

```text
Автор выбирает книгу, главу и задачу
  -> сохранение рабочего текста и плана
  -> сервер проверяет scope, версии, привязки и бюджет
  -> неизменяемый narrativeContext + выбранный текст
  -> агент пишет/разбирает в границах согласованного задания
  -> ответ + необязательные предложения закрытия с цитатами
  -> сервер проверяет ссылки и актуальность
  -> автор принимает либо отклоняет предложение
```

Сервер добавляет `APPROVED NARRATIVE FRAMEWORK` перед текстами глав. В блок входят: scope; ID/version/hash активных снимков; общий замысел и ограничения; текущие этапы и критерии; связанные родительские этапы; предпосылки с подтверждёнными исходами; будущие ограничения/запреты раскрытия; состояния проверки доказательств. Полный текст посторонних глав и все арки серии автоматически не добавляются.

`narrativeContext` — отдельное серверное поле `agent.message`, не часть manuscriptContext. Клиентское готовое поле отклоняется. Сборка выполняется независимо от ветки manuscriptChapters: планирование без текста разрешено; локальный documentSnapshot разрешён при проверенной привязке draft ID к chapterId; noteId не служит рукописью главы; importJobId с каркасом отклоняется 400. В chunks блок стоит после AUTHOR REQUEST и до textReviewContext/manuscriptContext. Для будущей главы без текста доступны планирование и создание нового текста, но не доказательства закрытия до сохранения рукописи.

В режиме работы по каркасу Google-главы сервер читает из сохранённого рабочего файла по chapterId → textBinding → key, локальные черновики — из store по draft ID. Переданные клиентом identity и хеш конкретной главы должны точно совпасть, иначе 409 «Сначала сохраните главу». Общая версия .book.json хранится для диагностики и CAS записи; изменение другой главы не делает этот текст устаревшим и не вызывает отказа. Это же правило применяется к версии локального черновика при неизменном тексте. Браузерный text не является источником narrative-запроса. Для каждого текста сервер фиксирует sourceIdentity, диагностическую workingVersion и SHA-256 главы в manifest; именно этот снимок получает агент и именно по нему проверяются предложения. Решения о 409, устаревании ответа и доказательствах сравнивают identity/хеш конкретной главы, а не общую версию файла. Сохранение главы и создание evidence валидируются синхронно в одном серверном критическом участке без await между проверкой файла и транзакционной записью; одиночный серверный lock остаётся обязательным. Последующая правка этого текста помечает результат устаревшим.

Содержание плана является авторскими данными, не системными инструкциями. Контракт агента: сохранять согласованный замысел и границы знания; не раскрывать будущий этап раньше заданного срока; при конфликте нового поручения с планом назвать точное расхождение и подготовить предложение изменения, без скрытого редактирования плана. Явное новое авторское решение допускается немедленно в рамках поручения, но постоянное изменение плана сохраняется через показанный diff и авторское действие. Агент не выдумывает закрытие и не превращает «закрыт ранее · проверить» в доказанный факт актуального текста.

Снимок фиксируется при staging запроса; в истории сохраняется manifest. До turn/start повторно проверяется активная версия. Если она сменилась — запрос не стартует и UI предлагает отправить заново. Если согласованная версия плана, привязка или хеш выбранной главы изменились уже во время генерации — результат маркируется «По предыдущей версии»; предложения закрытия не применяются до перепроверки. Новый ход всегда получает актуальный manifest; прежний план в истории чата не считается активным.

Предлагаемый бюджет: сохраняются 120 000 UTF-16 единиц для manuscriptContext с метаданными; дополнительно до 24 000 для narrativeContext с метаданными. Сумма этих двух блоков не более 144 000; бюджет глав не сокращается. Это не полный лимит prompt: AUTHOR REQUEST, textReviewContext, stagedDocument, selectedText, выбранные источники, workspaceContext и runtime manifest учитываются отдельно с существующими ограничениями; полный собранный prompt проходит preflight по доступному контекстному окну выбранной модели с резервом ответа. При неизвестной вместимости режим «Писать по каркасу» не запускается: UI показывает причину невозможности preflight. UI показывает размеры каждого блока и общий расход; дублируемый текст также считается. Превышение возвращает 413 `agent_context_too_large` со списком блоков и лимитов; никаких тихих усечений. Можно явно выбрать меньшую задачу, но её общие ограничения, предпосылки и запреты раскрытия обязательны. Если они не помещаются, запуск блокируется до пересмотра контекста автором.

Ответ агента с предложением закрытия содержит stageId/revision, planVersion, chapterId, textHash, точные цитаты и пояснение по критерию. UI принимает структуру только после серверной валидации, не по свободной фразе «этап закрыт». Автоизменение согласованного плана, авторской прозы и Google из этого ответа отсутствует.

Канал предложения — отдельный allowlisted инструмент `talewisp_propose_stage_closure` через существующий серверный tool-dispatch, не файловая запись из readOnly runner. Сервер проверяет аргументы по manifest активного requestId, сохраняет только pending-предложение и возвращает receipt/proposalId. Свободный текст ответа не парсится в операции. Инструмент не умеет согласовать план или закрыть этап. Несовпавшие версии дают stale/refused; UI показывает только предложения с квитанцией. Manifest сохраняется в отдельном `narrative_requests` по requestId и связывается с user/assistant message IDs, не восстанавливается из текста чата.

requestId для tool-call берётся из активного хода на сервере, а не из аргументов модели. Вызов после завершения/остановки хода отклоняется. Каркас с noteId разрешён только для обсуждения: заметка передаётся как дополнительный контекст, не как рукопись главы и не как источник доказательств закрытия.

Preflight всего prompt обязателен только в режиме «Писать по каркасу» и не меняет обычный маршрут без каркаса. UTF-16 лимиты служат ограничением размера блоков; вместимость окна отдельно проверяется официальным токенизатором выбранной модели по полному prompt с резервом 16 384 токенов на ответ и 8 192 на служебный контекст. Для шаблонов/скрытого контекста runner, не отражённых в доступной оценке, требуется подтверждённый контракт учёта; без него preflight не считается доказанным. Если окно, токенизатор или контракт неизвестны, этот режим не запускается и показывает точную причину; обход без проверки не предусмотрен. Обычный маршрут сохраняет существующие правила, включая `chapter_context_too_large`; новый `agent_context_too_large` относится к маршруту с каркасом. Поддержка preflight — обязательная проверяемая зависимость шага 4, а не уже имеющаяся возможность runtime.

## Данные и API

Хранить в SQLite приложения, рядом с app-owned проектными данными. localStorage — только восстановление несохранённого ввода. Не вкладывать план в `.book.json`: план книги должен переживать смену рукописи. Снимки и операции согласования транзакционны; CAS обязателен. Не менять схему рабочих рукописей ради самого плана.

| Сущность | Ключевые поля |
|---|---|
| narrative_plans | id, authorId/seriesId/bookId, kind book/chapter, chapterId?, draftVersion, activeSnapshotId |
| narrative_snapshots | id, planId, version, hash, immutable payload, approvedBy author, approvedAt |
| narrative_stages | В payload снимка: id, contentRevision, lineId, order, title, expectedChange, closureCriterion, prerequisites, disclosureConstraints, parentStageIds |
| narrative_chapters | chapterId, scope, textBinding, bindingVersion, bindingStatus |
| narrative_progress | Ключ planId + stageId + contentRevision; decidedInSnapshotId, state, actor, decisionReason, evidenceIds, CAS version |
| narrative_evidence | id, chapterId, sourceIdentity, workingVersion, textHash, quote/prefix/suffix/start/end, anchorState, validationState |
| narrative_proposals | id, requestId, snapshot refs, textHash, proposed action, evidence, pending/accepted/rejected/stale |
| narrative_events | operationId, scope, action, before/after refs, actor, time; журнал согласования/закрытия/возврата |
| narrative_requests | requestId, scope, immutable manifest, source hashes/versions, user/assistant message IDs, lifecycle status |

Связи и зависимости валидируются на существование, принадлежность книге и отсутствие циклов; parentStageIds ведут от главы к общим этапам. Нельзя ссылаться на неизвестные или архивные этапы как на действующие. Планы другой книги не принимаются из тела запроса. Каскадного удаления истории нет. При проектном relink перенос всего scope выполняется в той же транзакции, что и существующие scoped данные; до реализации и проверки этого контракта relink книги с планами отклоняется с объяснением.

Предлагаемые маршруты (ещё не реализованы):

| Маршрут | Контракт |
|---|---|
| GET `/api/books/:bookId/narrative` | Планы, активные снимки, прогресс и версии; проверка активного workspace |
| PUT `/api/books/:bookId/narrative/:planId/draft` | expectedVersion + operationId + полный валидированный черновик; 409 при конфликте |
| POST `.../:planId/approve` | expectedDraftVersion + shownHash + expectedActiveSnapshotId; согласовать ровно показанный снимок |
| POST `.../chapters/:chapterId/bind` | CAS привязки, явное подтверждение сопоставления и проверка источника |
| POST `.../stages/:stageId/evidence` | Снимок плана, версия текста, точное выделение; сервер валидирует якорь |
| POST `.../stages/:stageId/decision` | Закрыть/начать/вернуть; expectedProgressVersion + snapshotId + contentRevision + operationId |
| POST `/api/agent/message` | Клиент передаёт refs выбранного каркаса/этапов, сервер собирает narrativeContext сам |
| GET `/api/books/:bookId/narrative/operations/:operationId` | Квитанция/статус известной операции в текущем scope; 404 не означает подтверждённый успех |

`shownHash` вычисляет и возвращает сервер при GET/PUT черновика по канонической сериализации; клиент возвращает ровно этот хеш при согласовании.

Все мутации идемпотентны по operationId + hash тела в scope: повтор идентичного запроса возвращает прежнюю квитанцию, тот же ID с другим телом отклоняется. При потере ответа UI читает статус операции, не переигрывает согласование/закрытие новым ID. При 409 несохранённый ввод сохраняется для сравнения, без молчаливого merge. Проверки Host/Origin и размеров тела остаются действующими. Новые лимиты: максимум 1000 этапов книги, 200 этапов главы, 2000 глав, 20 якорей на одно решение; превышение возвращает явную ошибку, не обрезку.

## План реализации

| Шаг | Изменения | Проверяемый выход |
|---|---|---|
| 1. Домен и хранение | Новый `narrative-store.mjs`, версия схемы, транзакции, CAS, UUID глав, согласование | Пустые старые проекты работают; планы изолированы по scope, история не теряется |
| 2. Каркас в интерфейсе | Новый `public/narrative-panel.js`, модель и CSS; инспектор/оглавление/главы | Автор задаёт общую линию и сюжетку, видит diff и согласовывает версию |
| 3. Доказательства | Новый `narrative-evidence.mjs`, отдельный слой CodeMirror | Переход по фрагменту, ручное закрытие, stale после изменения, сохранение после reload |
| 4. Контекст агента | Новый `narrative-context.mjs`, server/agent/app integration | Preview совпадает с серверным manifest; согласованный план реально входит в staging |
| 5. Приёмка | Fixtures, browser QA, fresh Sol actual-diff review, Opus финал реализации | Пройден сценарий автора, scope и визуальное поведение подтверждены |

Зависимости: 1 → 2; 1+2 → 3; 1+2 → 4; 3+4 → 5. Реализация не должна перезаписывать уже имеющиеся незакоммиченные изменения редактора. Перед миграцией живой БД, перезапуском/развёртыванием потребуется отдельная проверка конкретного риска по проектным правилам; текущая проектная записка ничего из этого не выполняет.

## Приёмочные сценарии

1. Создать общую линию из трёх этапов и сюжетку будущей главы; перезагрузить UI — данные и порядок сохранены. Связать позднее с локальной или Google-главой, сохранив UUID.
2. Согласовать показанные версии; изменить черновик — агент продолжает получать прежний согласованный снимок. После согласования нового — получает новый. Перестановка с повторным согласованием сохраняет закрытия; новая contentRevision не наследует закрытие без решения автора. Изменённая revision родителя блокирует совместимость сюжетки до согласования связи. Повторное согласование связи не сбрасывает закрытия неизменённых локальных этапов.
3. Связать выделение с этапом, подтвердить закрытие — галочка в плане, счётчик главы, переход к правильному фрагменту и включаемая подсветка.
4. Повторить цитату, сдвинуть/изменить/удалить текст, заменить основную рукопись — ни одного ложного утверждения об актуальности; исторический зелёный контур с нейтральным флагом отличим от актуального закрытия. История доступна, неоднозначное сопоставление не применяется. Подменённый браузерный text и неверный hash дают 409 до runner; доказательства сверяются с тем же сохранённым снимком, что получил агент.
5. Закрыть этапы главы — общий этап остаётся открытым до собственного авторского решения. Вернуть этап в работу — история сохраняется, счётчик меняется.
6. Параллельные вкладки: конфликт черновиков/согласований/закрытия возвращает 409; старый ответ после A→B→A не меняет текущую книгу. Таймаут с повторным operationId не создаёт второе событие.
7. Писать по каркасу: перехваченный запрос к runner содержит правильные версии, критерии, предпосылки и ограничения; черновики и данные другой книги отсутствуют. Превышение бюджета не запускает модель.
8. Во время ответа согласовать новый план/изменить текст — старое предложение видно как устаревшее и не принимается к новой версии. Прямая подмена narrativeContext клиентом отклоняется.
9. Закрытие без цитаты обозначено отдельно; длинный/пересекающийся фрагмент, клавиатура, screen reader, узкий экран и совместимость с pending редакторскими предложениями проверены визуально и функционально.
10. Смена имени/порядка/ID источника, удалённая глава, запись новой главы в Google, relink проекта — нет молчаливого переноса доказательств и потери согласованных снимков. Vault и Google не меняются от действий с планом.

Проверки этого проектного задания: чтение перечисленных исходников; сопоставление всех четырёх частей ТЗ с разделами проекта; осмотр diff только нового документа. Тесты runtime и визуальная приёмка относятся к будущей реализации и сейчас не заявляются.

## Компромиссы

Цена решения: отдельные согласованные снимки и UUID требуют дополнительной модели данных, зато отделяют замысел от исполнения и от нестабильной нумерации Google. Консервативная перепроверка после изменения главы добавляет работу автору, но точное совпадение цитаты само по себе недостаточно для сюжетного вывода. Счётчики дают навигацию по этапам, а не оценку художественной готовности.

Рекомендацию нужно пересмотреть, если «общая линия» подразумевает прежде всего всю серию: тогда нужен отдельный series-scope план с явными межкнижными связями и правилами раскрытия. Текущий дизайн не выдаёт такое расширение за уже согласованную потребность.
